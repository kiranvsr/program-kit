# Changelog

## 0.5.4

Progress docs behind state, the tasks ready to start, and a stop hook (R570 in the program it came from). There, controllers let the hand-kept progress docs (a dashboard, a successor prompt) fall behind the program state and left agent slots idle during busy event-driven stretches; the user had to ask four times. The program's stop-gap was a script outside the repository run by its agent tool's stop hook. This release makes the check part of `pk drift`, provider-neutral, with the hook as an adapter. Everything is backward compatible: without the new `progress` section `pk drift` runs as before, with one more line, `D7 ok skipped: not configured`, and the ready list.

What changed:

- `pk drift` D7, progress docs behind state. The optional `progress` section of `program/checks.yaml` names `docs` (paths kept by hand) and `state` (paths whose commits change the program state), and optionally `quiet_when`. D7 drifts when a commit on the main branch touching a `state` path comes after the oldest of the `docs` paths' newest commits, judged by history (`<docs commit>..main`): a branch's state commit merged after the docs counts. It names the newer state commits (short sha and subject, at most six, then a count). Without the section it is skipped and says so. HANDOFF staleness stays D3. The gate and `pk doctor` check the section's shape. `kit/scripts/progress.py`.
- `pk status ready [--json]`: the not-started register tasks whose `depends_on` are all done or merged (ready), and those with exactly one dependency not yet done (near-ready, naming it and its status), leaving out any task with a worktree or a `task/<ID>` or `wip/<ID>...` branch. `pk drift` prints it after the checks, as information, never as drift.
- `pk drift --hook <adapter>`, the stop-hook form: D3 and D7 only, on the checkout. It prints nothing and exits 0 when both are clean; otherwise it prints the agent tool's block answer (for the one adapter so far, `{"decision": "block", "reason": ...}`), whose reason names the stale docs, the newer state commits, what to do (run the program's progress pass, republish its tracker, fill free agent slots or say why none fits) and the ready lines. It reads the hook's JSON on standard input and stays silent when the agent is already continuing because of this hook, and when `progress.quiet_when` (a shell command) exits 0. Standard output carries nothing but the answer; a problem is one line on standard error and exit 1, which never blocks.
- `pk hook install <adapter>`, `pk hook remove <adapter>` and `pk hook list` (`kit/scripts/hook.py`). Install merges a stop hook running `python3 <absolute path>/kit/scripts/pk.py drift --hook <adapter>` into the tool's local settings file, creating it if absent and keeping every other key and array; it is idempotent, re-points an old entry of its own at the current path, and refuses when the file is tracked by git or not git-ignored, saying which line to add to `.gitignore`. Remove deletes only its own entry. Neither ever writes the tool's shared settings file or any git hook.
- Docs: DESIGN sections 3 and 9.3, playbook 08 (run `pk drift` after every hand-back, gate, verdict, merge, ruling or dispatch; install the hook where the agent tool has an adapter), playbook 09 (D3 and D7 ok before a hand-off and in the successor's state check), README.

Design choices, each with its reason:

- The check lives in `pk drift`, not in the hook: any controller on any agent tool runs the same check by hand; the hook only makes one tool run it at the right moment.
- Nothing in git hooks: a git hook fires inside merges and pushes, where a refusal leaves a half-done merge or a refused push. Nothing committed: one person's agent tool settings do not belong to everyone, so install refuses a tracked or unignored settings file.
- History, not clock time, decides "after": commits made in the same second, and a branch's status commits merged after the docs, are judged correctly.
- The hook runs only D3 and D7, never the full report: it runs every time the agent stops, and the full report builds a temporary worktree and runs the regenerators.
- The adapter names are written in fragments in the kit's code: the kit names no vendor in its files, yet an adapter has to use the tool's own command and directory names.

Upgrading from 0.5.3: `sh install.sh /path/to/your-repo --upgrade`. Nothing in `program/` has to change. To use D7, add the `progress` section to `program/checks.yaml`; to have your agent tool run it at each stop, run `pk hook install <adapter>` (`pk hook list` names the adapters) and remove any hand-made hook that did the same.

## 0.5.3

Planted-bug chunks as kit records (R561 in the program it came from). There, a full-tier task carries 150 to 250 planted-bug rows, and gap rows (QA's surviving plants, spec-QA gaps) arrive in fix rounds. Judged as a chunk, 110 gap rows took 863 s; inside a gate they hold the machine for about an hour. The program judged them in a separate run into a side file of the producer's, `program/evidence/<ID>/gap-plants-extra.json`, and `pk merge` refused it after QA had accepted (F-0403): nothing unbound may land after the reviewed commit. That rule stays. The chunk results are now a kit record, bound to the gate record, that acceptance and merge understand. Everything is backward compatible: every record, pointer and producer written before reads and runs as it did, and a producer that marks no row `defer` gets the 0.5.2 rows.

What changed:

- Deferred rows. A producer marks a planted-bug row `defer: true` (in the row, as `serial`). The gate records every row; a deferred row carries its full definition (path, find, replace, build_argv, test_argv, serial), its `definition_sha256` and `deferred: true`, and no verdict, in its table position. It is not judged at gate time. `planted_bugs_all_killed` and the gate's pass count only the judged rows; the self-test row still runs. The gate's last lines before `OK:` say how many rows are deferred and print the exact `pk gate plants ... --all-pending` command.
- `pk gate plants <ID> --branch task/<ID> (--rows ID,... | --all-pending) [--workers N] [--rejudge] [--timeout S]` (`kit/scripts/plants.py`). It judges deferred rows of the task's latest results record at that record's `head`, never the branch tip, each in a clean detached mirror, with the 0.5.2 pool (serial rows after it, every verdict that is not a clean kill judged again alone, the resource-error recheck). The definitions come from the record: the producer is never run again, and a row whose definition no longer matches its digest is refused, as is a row that is not deferred or that a plants record bound to the same record already judged killed (unless `--rejudge`). It appends an immutable record of the new kind `plants`, `program/evidence/<ID>/plants/<utc>-<sha256[:12]>.json`, through the store, naming the task, `part_of` (the results record's path and digest), the head, the kit version, the workers and seconds, and each row's verdict in the gate's row schema with `serial` and `definition_sha256`. Several chunks may exist and may run any time after the gate, while QA reviews too. It takes no machine lock. Schema: `kit/templates/plants.schema.json`.
- The pointer `latest.json` gains an optional `plants` list (digest, path, part_of, head, produced_at per record); old pointers stay valid. `pk evidence validate`, `pk evidence history`, `pk doctor` and `store.integrity` cover the new kind and folder: every file in `plants/` must be listed, and every listed record must resolve to its digest and, with the schema check, parse as a plants record.
- Coverage. Evidence is complete when every deferred row of the latest results record has a killed verdict in a plants record whose `part_of` is that record and whose head is that record's head. `pk evidence accept`, `pk status set <ID> done` and so `pk merge` refuse until it is, naming the rows not judged yet, the rows judged and not killed with their verdict, and the command to judge them. A full-tier acceptance's own planted-bug quota is unchanged.
- Merge. After the reviewed commit a branch may add records directly in `plants/`, as in `results/` and `acceptance/`. A plants record added then that is bound to another results record stops the merge with a message naming both; one that fails integrity stops it as before.
- The early refusal (the root of F-0403). The late-work rule moves to `kit/scripts/latework.py` and runs at `pk evidence accept` and `pk status set <ID> done` too: committed late work after the record's head, and uncommitted files under `program/evidence/<ID>/` that the kit does not write, are refused at the first of those steps, naming the file, the allowed paths and `pk gate plants`. Before its long run, the hand-back gate names such files when QA had accepted the latest record (the run then writes a new record, which QA must accept again). A gate run whose producer appends no record over such late work passes as before (the record still holds for its inputs) but prints a `late work:` line naming what the merge would refuse.
- Reuse. When the gate reuses a record on unchanged code (0.5.2), the plants records bound to the reused record (or to one it reused in turn) count for the new record: they were judged on the same code. The new record names them in `plants_reused_from`; coverage follows `reused_from`.
- The time estimate. Records now carry `planted_bugs_timing` (seconds, judged rows including the self-test row, workers). Before a run that does not reuse a record, the gate estimates the judged rows' time from the last record's row count and timing and this run's workers; at 80% of the evidence step's 3,600 s limit it prints an `evidence estimate:` warning naming `defer: true`, `evidence.plant_workers` and splitting the task. It never fails the gate.
- Docs: DESIGN sections 3, 5 (steps 4, 6, 7a, 8), 9.2 and 13, playbooks 07 and 08, the implementer and QA briefs, and the results schema (deferred rows, `planted_bugs_timing`, `plants_reused_from`).

Design choices, each with its reason:

- Definitions live in the gate record, with a digest: a chunk judges exactly what the gate recorded, at the gate's head, and never needs the producer again, so a fix round cannot slip a changed row into an old record.
- Plants records are their own kind with a pointer list rather than an amendment of the results record: records are immutable, and several chunks of one record must coexist.
- Coverage is derived from the records every time, never stored: acceptance, `done` and the merge read the same function.
- The gate's own late-work check only warns: in a normal fix round the new record binds the tip, and a record that still holds for its inputs stays valid evidence of its head (the 0.4 rule); acceptance and done are where it refuses.
- The estimate warns at 80% of the limit and uses only a timed record: the producer's own commands share the evidence step, and a guess without a measurement would be noise.

Upgrading from 0.5.2: `sh install.sh /path/to/your-repo --upgrade`. Nothing in `program/` has to change. To use chunks, a producer marks gap rows `defer: true`; after the gate, run the printed `pk gate plants` command (in chunks with `--rows`, or `--all-pending`) and commit each plants record with `latest.json`. A program that judged gap rows into its own file stops doing so: accept, `done` and the merge refuse such a file after the reviewed commit.

## 0.5.2

Faster hand-back gates (R546 in the program it came from). There, one gate took about an hour while the machine (10 cores) mostly idled: the build and test steps 5 to 8 minutes, the producer re-running the same suites about 8 minutes, and the planted bugs 2,946 s for 151 rows, 129 baselines and the self-test row, judged one at a time, close to the evidence step's 3,600 s limit. All three changes are opt-in: nothing in `program/` has to change, every record and producer written before reads and runs as it did, and a program that opts into nothing gets byte-identical rows.

What changed:

- Parallel planted-bug judging. `Evidence.planted_bugs(table, build, test, timeout=None, workers=None)`: `workers` rows at once; None means `PK_PLANT_WORKERS`, else `evidence.plant_workers` of the committed `program/checks.yaml`, else 1. With one worker the run is the 0.5.1 run. With more, every baseline and every row runs in its own fresh `git worktree add --detach` mirror of the recorded head, never shared; worktree add and remove are serialised under one lock so git's index lock never races. A table row may say `serial: true`; serial rows, their baselines and the self-test row run alone after the pool. Rows that use a browser, an e2e server or a fixed port must be serial. A kill still needs a passing build and a non-zero test exit. Every pool verdict that is not a clean kill is judged again alone and that verdict recorded: a row that did not build or was not killed, a kill whose test output shows a resource error (EADDRINUSE, address already in use, port is already allocated, ECONNREFUSED on localhost, a timeout, out of memory, ENOMEM, ENOSPC, EMFILE), and every kill of a test whose baseline failed in the pool. A baseline that fails in the pool is run again alone before it can fail the run. The rows keep the table order and schema and gain only the optional `judged` field (`parallel`, `serial`, `serial-recheck`); `test_output_sha256` is computed as before. One progress line per finished baseline and row goes to standard output. Measured on a kit fixture (12 rows, 12 baselines and the self-test row, each test about 1 s): 29.0 s with one worker, 16.1 s with two, 8.8 s with four, 5.5 s with eight.
- Reuse of evidence on unchanged code (`kit/scripts/reuse.py`). With `evidence: {reuse_unchanged_code: true}` on main, the hand-back gate reuses the task's latest results record when it passes the gate's own checks (every command as expected, every planted bug killed), is not a gate record, its head is an ancestor of HEAD, `kit/VERSION` is the same, and the code is byte-identical between that head and HEAD by git mode and blob id: every tracked path outside `program/` except the optional `evidence.reuse_ignore` paths (the kit and every lockfile are always compared), `program/checks.yaml`, the task's `program/tasks/<ID>/`, its producer folder without records and pointer, and the optional `evidence.reuse_compare` paths under `program/` (the producer's shared tools). It then skips the test step and `produce.py` and writes a new record that copies the old one's commands and planted-bug rows, names it in `reused_from` (`{path, digest, head}`), and binds the new head, main and merge base with the old record's input paths hashed again at HEAD; build, compile check, scan, extra gate, the PLAN commands and the drift report still run. One `evidence reuse:` line says which record is reused or why not. `pk gate handback --no-reuse` runs everything.
- No duplicate suite run. The gate's test step hands each command's argv, exit and full output to `produce.py` in a JSON file named by `PK_GATE_TEST_RESULTS` (a temp directory outside the worktree, removed after the evidence step). `Evidence.reuse_gate_test(label, argv, parse=None, expect=0, timeout=None)` returns the row `run_command` would record from that output when the argv is byte-identical to one the test step ran in this root at this head, marked `from_gate_step: "test"`; otherwise it runs the command. Producers opt in by calling it; the example producer does.
- `checks.yaml` gains the optional `evidence` section (`plant_workers`, `reuse_unchanged_code`, `reuse_ignore`, `reuse_compare`); the gates and `pk doctor` refuse a section of the wrong shape by name. The results schema documents the three optional fields, and `pk evidence validate` checks them when present.
- Docs: DESIGN sections 5 and 9, playbooks 07 and 08, the implementer brief, the `checks.yaml` template and the example producer.

Design choices, each with its reason:

- Threads, not processes: every job is a subprocess, so the GIL is not a limit, and the jobs share the lock and the progress printer.
- A fresh mirror per job rather than one per worker restored between jobs: `git worktree add` costs about half a second on a 3,300-file repository, and a fresh mirror cannot carry anything over from the previous row.
- Every non-kill is re-judged alone, not only kills with a resource error: in a passing run there are none, so it costs nothing, and in a program whose judge checks its own needle (where contention turns a kill into a false survivor, not a false kill) it removes the pool's other failure mode.
- Reuse compares git trees, not the old record's inputs: a record that binds every tracked file would never be reusable after a bookkeeping change, which is the case the reuse is for. The record names what it copied, so QA can see that the commands ran at an earlier head with the same code.
- The test-step hand-over covers the `test` step only: the scans and extra gate commands are cheap and their argv rarely matches a producer's.

Upgrading from 0.5.1: `sh install.sh /path/to/your-repo --upgrade`. Nothing in `program/` has to change. To opt in, add to `program/checks.yaml` on main, for example `evidence: {plant_workers: 4, reuse_unchanged_code: true}`, and mark serial rows in the producers that need it; a producer opts into the test-step reuse by calling `reuse_gate_test` for its test-suite commands.

## 0.5.1

Three speed-ups a program proved locally, so a spec and a fix round each cost fewer gate runs. Everything is additive: nothing in `program/` has to change, every record written before reads as it did, and no command changes what it accepts.

What changed:

- `pk spec precheck <task folder or ID>` (`kit/scripts/precheck.py`): the spec author's check before spec QA, one line per finding, exit 1 on any. PC-1 the PLAN's plant rows (a table under a `## ` heading that names plants, first column `#`; or the folder's `plants.py` or `plants.json`) each name a killing test and, where the table has the column, a needle; every plant has a PLAN row and the reverse; every find occurs exactly once in the file it names; every `case:` or `check:` needle is in the plant's test file and every killing test is in a test file. PC-2 no needle is a proper prefix of another label in the same test. PC-3 every Failure Modes row has a plant (by its Row column, else by a test it names). PC-4 a `standin.patch` applies to main and three-way onto every task branch main does not contain (local `task/*` and `origin/task/*`, one line per tip, the task's own skipped), by file. PC-5 the gate's own parser reads the `## Exact Commands`. The code is the stand-in applied to a private index (the repository is not written to), else the task branch; without either the code checks are skipped with a note. Without any plant table the plant checks are skipped with a note and each failure mode must still name a test; `--require-plants` makes that a finding, for a program whose PLANs always carry the table. Reason: in the program it came from, spec QA rounds kept finding the same mechanical faults (a find that occurs twice, a needle that is the prefix of another label, a stand-in that no longer applies), and each one cost a review round.
- `pk spec precheck --build`: PC-6, each plant row's replacement, applied alone to a throwaway mirror of the code, must pass main's `build` and `compile_check` commands; the rows that do not build are named with the failing command and its error line. The unmutated code must build first. Reason: the program lost a checkpoint because three replace cells (`if (false) ...` removing a type guard) failed a strict type check, so the gate recorded them `build failed` rather than killed, which a gate run found hours later.
- `pk gate rejudge <ID> --branch task/<ID> --rows <IDs> [--baseline] [--timeout SECONDS]` (`kit/scripts/rejudge.py`): re-runs only the named planted-bug rows the way the evidence runner does, on a clean detached mirror of the branch tip: one edit, the row's build, the row's test, the runner's verdict (`killed`, `not killed`, `build failed`), with the build output's tail. It says on its first and last lines that it is not gate evidence, and writes no record, pointer or status. The rows come from the producer's `rejudge_rows()` when it defines one (rows in the shape of a results record's planted-bug row: `id`, `path`, `find`, `replace`, `build_argv`, `test_argv`; the producer is imported in its own process and its main block does not run), else from the task's latest results record on the branch. It exits 0 only when every named row was killed. Reason: between checkpoints a fixer had to re-run the whole gate, or write a one-off script, to learn whether a changed row now builds and is killed.
- `evidence.PlantJudge`: the mirror, restore and verdict of `Evidence.planted_bugs`, usable one row at a time and with any ref; `pk spec precheck --build` and `pk gate rejudge` both use it. The evidence runner itself is unchanged (its restore and removal moved into a shared base class).
- Task files stay on main. The implementer brief says never to edit anything under `program/tasks/<ID>/` on the task branch: a needed SPEC, PLAN or table change goes in the hand-back, the controller makes it on main and the branch merges main. Every "differs from main" line of the gates (SPEC, PLAN, review, CONTRACT and BRIEF) now ends with that fix, and the controller brief and playbook 08 say it once each.
- Playbook 07, step 5a: the author runs `pk spec precheck` before handing the SPEC and PLAN back; the spec-QA brief runs it with its mechanical checks. Playbook 08 names `pk gate rejudge` for fix rounds.

Design choices, each with its reason:

- The kit takes no machine lock, in the gate or in the two new commands: a lock is a property of the machine a program runs on, not of the kit. A program that serialises heavy runs wraps `pk gate rejudge` and `pk spec precheck --build` in its lock as it wraps the gate.
- `--build` runs main's `build` and `compile_check`, not a producer's per-row build: at spec time there is no producer yet, and those commands are what the gate's own build step runs.
- The rejudge rows come from the producer when it can say them, because a row changed since the last gate run is exactly the one a fixer wants judged; the latest record is the fallback every task already has.
- A "differs from main" line keeps its first words, so a script that matches the start of the line still matches; a test that compared the whole line needs the hint appended (`gate.FIX_ON_MAIN`).

Upgrading from 0.5.0: `sh install.sh /path/to/your-repo --upgrade`. Nothing in `program/` has to change. A program with its own spec precheck can call `pk spec precheck` instead (with `--require-plants` to keep a missing plant table a finding); a producer that defines `rejudge_rows()` gets re-judged rows that follow its current table.

## 0.5.0

Sharper review of full-tier specs at a lower cost, and a report of the drift between a program's documents and what they are generated from. It comes from a trial a program ran on three full-tier specs and its merge batches; what the trial dropped is listed below, with its numbers, so that a later program need not run it again. Everything is additive: nothing in `program/` has to change and no existing rule is removed or tightened. A program that adds neither the `drift` section nor the step 6a reviews runs as before, apart from the two hand-off fixes.

What changed:

- `pk drift` (`kit/scripts/drift.py`), with `--rev REV` (default HEAD) and `--strict`: a report-only command that checks one commit in a temporary detached worktree, removed afterwards, so nothing in the checkout is written. D1 regeneration is a no-op: the commands of a new optional `drift.regenerate` list in `program/checks.yaml` (argv lists, run without a shell), then, once stage 6 is approved, the kit's own `pk trace sync` and `pk briefs check`; a changed YAML file counts only when its parsed data changed. D2 approvals: `pk interview next` names no approved stage whose files changed. D3 the hand-off: `pk handoff check`, run on the real checkout before the temporary worktree exists (that worktree would otherwise be listed in the hand-off), and skipped for another revision. D4 an optional `drift.docs_vs_migrations` pair `glob` and `doc`: every matching file is named in the document by its name, its stem or its leading number. D5 every `done` task has an acceptance record. D6 `pk register validate`, `pk status validate` and `pk trace validate` at the highest approved stage. It exits 0 unless `--strict` is given and a check drifts. The gates and `pk doctor` accept the `drift` section and refuse one of the wrong shape; the `checks.yaml` template shows it in a comment. Reason: in the trial a backtest found both known drifts (a generator's output not regenerated and a stale stage approval) in 5 to 6 seconds, and live runs found two real misses in a controller's own change (a matrix claim and the task briefs not regenerated).
- KF-14: `pk handoff check` does not compare the lines under the generated block's Task worktrees heading (each worktree's head and clean or dirty state, and the short-lived worktrees of gates and agents). Reason: any commit or running agent changed them, so the check flapped; in the trial this was the one remaining false alarm of the drift report. Every other line is compared as before, the heading included, and `pk handoff update` still writes the lines as they are.
- KF-15: every hand-off budget refusal (`pk handoff check`, `pk record`, `pk merge`, and now `pk handoff update`) names the section, its size and the bytes over (`the Next steps section is 2539 bytes, 491 bytes over its budget of 2048`), and `pk` prints it on standard output as well as standard error (`common.Refusal`). `pk handoff update` writes the block first and then, over either budget, exits 1 with that line; it used to exit 0 and say nothing about the budget. Reason: a caller that discarded one stream never saw why the hand-off had stopped being fit to hand over.
- `kit/rubrics/`: `tenancy-security.md` (TS-1 to TS-9), `failure-modes.md` (FM-1 to FM-8), `challenger.md` (CH-1 to CH-4) and a README with the zero-context rule: a reviewer gets only the SPEC, the PLAN, the CONTRACT if any, the files they cite and one rubric, and no rulings, hand-back or controller summary.
- `kit/briefs/lens.md`: the zero-context reviewer's brief. It reads its documents in full (a first trial run that only searched them missed findings), writes one line per finding, `ID | severity | anchor | finding | exact fix` with the rubric item as ID, at most fifteen, into its own scratch folder, and never writes to the repository, builds, runs tests or uses the network.
- Playbook 07, step 6a, full tier only: after the author hands back and before spec QA, the tenancy-security lens (class A) and the failure-modes lens (class C) run in parallel; the challenger (class C) runs on the open points before any of them goes to the user, and its new options are shown beside the author's.
- `kit/briefs/spec_qa.md`: on the full tier spec QA reviews blind first (phase 1, its findings written before it opens a lens report), then in the same run rules on every lens row in `review.md` as `SAME`, `NEW-HIGH`, `NEW-LOW`, `FALSE` or `REJECT` (phase 2), and applies the ones it accepts as numbered findings with their exact fixes, which the author makes as for any other finding. There is no synthesizer and no separate judge. Its report gains a Lenses line.
- Playbook 08 runs `pk drift` after each merge batch. The reading table of playbook 09 has the new sizes (controller 49.3 KB, spec QA 13.9 KB, both under their 0.2.0 ceilings) and says what a lens reviewer reads.

The trial, and what it dropped. Three full-tier specs: a replay of an accepted spec whose class B spec QA (7 findings, 374k tokens) was the reference, and two live specs on which the lenses ran first and spec QA ran blind to them, then ruled on their rows. Six lenses were tried, plus a synthesizer and a challenger.

- Dropped, the zoom-out lens (simplicity, scope, reuse): no cut taken on any of the three specs, about 300k tokens in all; the cuts that mattered came from the user's own change requests.
- Dropped, the comprehension lens (a naive reader): 6 genuine gaps of 45 raised, all wording, and 16 false, at 88k to 118k tokens a spec on any model class, since reading the documents costs most of it.
- Dropped, the plant-rigour and readiness lenses: nothing a spec QA or a stand-in build does not already catch; 14 of their 23 rows on the replay were rejected.
- Dropped, the synthesizer: it merged 66 rows and filtered none, so a separate judge (213k tokens) had to sort them, and 27% were useful; lenses and synthesizer together cost 196% of the reference. Spec QA's phase 2 does the judging instead.
- Kept, the tenancy-security and failure-modes lenses: each found one serious defect the blind spec QA missed (two concurrent requests racing with no lock, so a stored deadline and its multiplier could disagree; four statements that bypassed both of the repository's tenant guards), and together they found both important findings of the replay. On the live specs they found 2 of spec QA's 14 and 2 of its 8 findings and missed a cross-document blocker, so they add to spec QA and never replace it.
- Kept, the challenger: options adopted on both live specs, at 56k to 67k tokens each, before the user saw the points.
- Kept, rubrics as files: every reviewer cited rubric ids, and a lens brief with its rubric is about a third of a spec QA brief.
- Cost of the kept form per full-tier spec: tenancy-security about 110k to 160k tokens, failure-modes 75k to 90k, challenger 45k to 65k, about 230k to 315k in all, against 380k to 520k for spec QA itself.

Design choices, each with its reason:

- `pk drift` runs the kit's checks with the kit that runs it, in process, against the worktree of REV; the program's own regeneration commands run as subprocesses there. D1 runs last because it writes into the temporary tree. The trace sync, briefs and trace checks wait for the approvals that make them meaningful, so a program in discovery does not drift on documents it has not written yet.
- KF-14 changes what `check` compares, not what `update` writes: the worktree list stays in the hand-off for a successor, it just no longer decides staleness.
- Spec QA's "never fix the spec yourself" stands: phase 2 turns the accepted rows into findings, and the author applies them.

Upgrading from 0.4.1: `sh install.sh /path/to/your-repo --upgrade`. Nothing in `program/` has to change. Scripts that run `pk handoff update` on a hand-off over its budget now see exit 1 with the reason on both streams; trim the section it names. To use `pk drift`'s optional checks, add a `drift` section to `program/checks.yaml` (see the template); without one, D1 runs only the kit's own regenerators and D4 says it is not configured.

## 0.4.1

Fixes for the findings a program recorded while running kit 0.4.0 (KF-1 to KF-9). Nothing in `program/` has to change: every file written by 0.4.0 reads as it did, evidence records included.

What changed:

- KF-1: `pk handoff check` on a hand-off whose markers hold nothing yet (every new program, since `pk init` and `install.sh` write no block) says `program/HANDOFF.md has no generated block yet (a new program); run: pk handoff update, then commit it` instead of calling it stale; it still exits 1, and a state that does not read is still reported first. `00_START.md` step 2 says so. Reason: the first check of every program said stale, which reads as something gone wrong. Running `handoff update` from `install.sh` was the other option; it was not taken because the block names a commit and the branches not merged into main, so it fails in a repository without a commit on main, and the installer promises to commit nothing.
- KF-2: the generated hand-off block has an Interview section, after the Now list, whenever `program/ledger.yaml` exists: the stage `pk interview next` names with its topics closed and open (or "discovery complete" at stage 7), the files changed since that stage's approval when there are any, and over the whole ledger the blocking questions unanswered and the assumptions unconfirmed, counted with their first ten IDs. Without a ledger the section is omitted; a ledger or approval that does not read is one line naming the command to run, never a traceback. Reason: during stages 1 to 6 the block said nothing about the interview, so a takeover had to run `pk interview next` and `report` before it knew where discovery stood. After upgrading, `pk handoff check` reports a program with a ledger as stale once: run `pk handoff update` and commit it.
- KF-3: `pk dashboard <out.html>` (optional, `kit/scripts/dashboard.py`: one script, one template string) writes one self-contained HTML page: the generated hand-off block as `pk handoff update` would render it now, the register with each task's status and tier, the status counts, the gates of `program/gates.yaml` with the status of the tasks that prove them, the cost log by task and by model with the agents past the threshold, and the open follow-ups. It reads only kit-managed files, writes only the file it is given, and the page has no script, no external asset and no clock time, so the same state gives the same bytes. Reason: programs kept a hand-maintained dashboard and their own generator beside the kit. `docs/DESIGN.md` section 14 is amended: a served or interactive dashboard stays out of scope, and the generated hand-off block stays the kit's view of the state; the page only re-renders what the kit already holds, adds no state and decides nothing (the 0.3.0 entry "No dashboard" stands for that sense).
- KF-4: `pk cost add --task ID` refuses an ID that is neither a task in `program/register.yaml` nor an ad-hoc task in `program/controller-state.json`, naming both and the way out; `--allow-unknown` logs it anyway. Reason: a typo, or an ad-hoc ID logged before `pk record --adhoc` created it, silently made an orphan line. Without a register (during discovery) only ad-hoc tasks are known. Existing lines, orphans included, are never checked: `pk cost report` and the hand-off read the log as before.
- KF-5: `pk interview amend N` prints, after the changed paths, one line `amended stage N: K changed file(s) re-hashed into program/approvals/stage-N.json` (exit 0). Reason: it printed only the paths, so nothing said the approval had been rewritten. `no changes` is printed as before. Scripts that read the output line by line see one more line.
- KF-6: a gate id that does not match is refused with the pattern in the message (`G-<NAME>, pattern G-[A-Z0-9][A-Z0-9_]*: NAME is capitals, digits and _, no hyphen`), by `pk trace validate`, `pk gate validate` and the other gate commands, and by `pk register validate`. Reason: `G-R1-CORE` was refused with "expected G-<NAME>", which does not say that NAME takes no second hyphen. The pattern itself is unchanged.
- KF-7: `pk doctor` holds back its warning about a `tiers` path that covers no tracked file while no task has a status record past `not_started` (none at all included), and prints one `note:` line on standard error saying how many it held back and why. Reason: before any code exists every listed full-tier path covers nothing, so the warning fired on every entry from the first day. A status record that does not read counts as started, so it never hides the warning. The exit code and `doctor: ok` are unchanged.
- KF-8: `pk record` prints, after its commit, one line naming the changed and untracked files under `program/` that it left out (`not in this commit, changed under program/: ...`), with the two ways to land them: commit them with git, or run the step with `--no-commit` and commit everything together. It still stages nothing but its own files. Reason: a ruling and the artifact edits it asked for landed in separate commits with nothing saying the edits were left behind. Staging `program/` behind a flag was the other option; it was not taken because a sweep of `program/` can take a half-written status file or an evidence record into a ruling commit, which the evidence and status rules keep to their own commits, and `--no-commit` already covers the one-commit case.
- KF-9: a results record's `inputs` is written as a list of `{"path": ..., "sha256": ...}` objects sorted by path, no longer as a mapping of path to digest. Reason: a mapping puts a path that holds a word such as `token`, `secret`, `auth` or `key` and its 64-character digest on one JSON line, which a secret scanner's generic-key rule reports, so a committed record failed every later scan. Every reader (`pk evidence validate`, `accept` and `lint`, the hand-back gate, `pk gate binding`, `pk merge`, `pk stale`, `pk status set ... done`, gate records' child rows) accepts both shapes through `store.input_digests`, so records written by 0.4.0 stay valid and are never rewritten. A digest prefix (`sha256:<hex>`) would also have defeated the rule, but it changes the meaning of every value and relies on the scanner's character class; the list keeps each value a plain digest and separates it from the path structurally. Records carry no schema version of their own (the pointer's `schema_version` stays 1), and the shape says which form a record holds. `Evidence.inputs` and `hash_inputs` still return a mapping.

Upgrading from 0.4.0: `sh install.sh /path/to/your-repo --upgrade`. Nothing in `program/` has to change. Evidence records written by 0.4.0 keep their mapping of inputs and stay valid; new records use the list. A program with `program/ledger.yaml` sees `pk handoff check` report the hand-off as stale once, because the generated block gains its Interview section: run `pk handoff update` and commit it. `pk cost add` now refuses an ID that is not a register or ad-hoc task; pass `--allow-unknown` where a run is logged against anything else on purpose.

## 0.4.0

A release-level statement of health, and a shorter wait at every gate. The evidence model of 0.2.0 and the tiers of 0.3.0 are unchanged; a program upgraded from 0.3.0 runs exactly as before until it adds `program/release-set.yaml` or sets `parallel_steps`.

What changed:

- `pk status reopen <ID> --reason TEXT [--role qa [--reject]]`: the documented way back for a branch marked `done` (late work after acceptance, or a QA rejection), with the reason kept as an audit line in the status history.
- `pk merge` and `pk evidence validate` check that every record in the store parses as a record of the kit's schema, not only that its bytes match its name; a file named after its own digest that is not a record is refused. The hand-back gate and `pk doctor` do not schema-check the whole store; merge and validate do.
- `pk worktree finish` asks the container tool for each item's compose project label and removes only an exact match, whatever the tool's own `--filter` returned.
- The example-neutrality test reads only the files git tracks in `examples/tiny-service`.
- `pk fingerprint run|plan|validate|show|coverage` and `program/release-set.yaml`: one committed record per commit that runs the project's release set on parallel tracks and derives per-test tables, with readers for how far the tree has moved since and which rows of a task's latest record it covers. Reason: a results record binds one task, so "the whole release set passed at commit X" could only be answered by re-running every task's commands.
- `parallel_steps` in `program/checks.yaml` (default false): the hand-back gate and the merge check run `test`, `scan` and `extra_gate` concurrently and print them in the serial order, so the result is the one the serial run reports. Reason: the three steps are independent and the longest of them, not their sum, should set the gate's wall time; it is opt-in because commands that write into the tree cannot share it.
- Working rule W12, fast default with the slow set in the release set: the `test` step finishes in minutes, slow cases sit behind one environment variable and run in their own release-set tracks. Reason: a thirty-minute suite at every hand-back makes agents skip it or wait on it.
- The kit's own tests follow W12: the cases that build whole repositories, run the gate end to end or install the kit sit behind `KIT_TESTS_SLOW=1` (`kit/tests/_slow.py`), so the default discovery run takes about two minutes instead of eleven and `KIT_TESTS_SLOW=1` still runs every test. A test fails when a module outside the documented six imports the gate.

Design choices, each with its reason:

- The fingerprint is a record per commit under `program/evidence/fingerprint/<head12>/`, outside the per-task store, because it binds a commit and a release set rather than one task's inputs; it is immutable like a task record, and a run at a commit that already has a tracked record is refused rather than rewritten.
- The record is committed only when it is complete and every command was as expected, by the controller, in a plain commit of exactly that directory; a red run stays uncommitted so that main never carries a fingerprint that claims less than green.
- No run store or replay: the kit never re-binds task records, QA runs commands fresh by design, and the merge check runs on a trial-merge commit, so a cached result keyed by commit would never be hit.
- Coverage is computed on read and never written next to the record, so a committed fingerprint is never touched after the fact.
- Absolute paths are refused by a token rule (a reserved prefix after nothing, an option, or punctuation is absolute; after a path segment it is not), so `cwd=/tmp/x` and `-Wl,-L/Users/x` are caught while `tests/tmp` and `src/home` run; environment values are scrubbed and refused only in free text (output tails, toolchain lines, problem strings), because a value such as `test` is also a word in test names.
- `parallel_steps` is off by default because the three steps share one tree, and only the program knows whether its commands can.
- The kit's own slow tests are gated rather than trimmed, and the manifest does not change, because `kit/tests/` is not installed into a program.

Upgrading from 0.3.0: nothing in `program/` has to change. To use the fingerprint, copy `kit/templates/release-set.yaml` to `program/release-set.yaml`, fill the entries, add that path to `guarded_files` in `program/checks.yaml`, and run `pk fingerprint run` from a clean tree at the commit you want to attest.

## 0.3.0

Faster and cheaper runs without a weaker process. The evidence model of 0.2.0 is unchanged (committed, append-only records; latest wins; a record binds only its inputs), and hard rules 1 to 20 and the twelve evidence rules are word for word what they were. Nothing in `program/` has to change to upgrade.

What changed:

- **One rules file.** `kit/rules/RULES.md` replaces `HARD_RULES.md`, `EVIDENCE_HONESTY.md` and `THROUGHPUT.md`: part 1 hard rules, part 2 working rules for every agent, part 3 evidence honesty, part 4 the controller's rules. The briefs, the playbooks, the seed rulings, `docs/DESIGN.md`, the README and the successor prompt point to it instead of restating it. Each role reads its own brief, its parts of the rules and `program/COMMON.md`; `kit/playbooks/09_handoff.md` lists the files with sizes, and a test checks the table.
- **Verification tiers.** A task is `full`, `standard` or `light`, recorded in its status record at dispatch and changed only by a ruling (`pk status set --tier`, `pk status tier`). The gates read the tier from main and enforce it. A light task ends at the new status `merged`.
- **Fast path.** `--fast --ruling R<n>`: one `BRIEF.md` and a ruling replace SPEC, PLAN and spec QA. Refused for the full tier by the status machine and both gates.
- **Parallel work.** `pk worktree review <ID>` (a detached review worktree, a diff file and a stat file that names what the diff leaves out; run again, it moves to the new commit for a re-review), integration rounds (`pk integrate start`, `check`, `close`, `pk merge <ID> --round NAME`), a contract-first template, and QA no longer limited to one branch at a time. Merges stay one at a time.
- **One command per step.** `pk merge <ID>` (merge check, merge, claims, hand-off, bookkeeping commit), `pk record` (ruling, state, hand-off, commit), `pk worktree finish <ID>` (worktrees, merged branch, named symlinks, and the containers and volumes that carry the exact compose project label; never forces).
- **Tracking.** `pk followups` (IDs, close, tag, duplicates; a follow-up is never deleted and its number never reused), `pk adhoc` (work outside the register), `pk cost` (an append-only log of subagent runs, with a fresh-agent threshold). The generated hand-off block opens with a Now list carrying each task's tier, what a blocked task waits on and every open integration round, counts the done tasks by tier, lists a parked task with the decision it waits on, and shows the newest fifteen rulings; `pk handoff check` fails over a size budget. `pk record` writes everything the block says about the controller (`--now`, `--note`, `--queued`, `--parked`, `--handoff-budget`).
- **Dispatch hygiene.** `program/COMMON.md`; brief sections "Decided (do not reopen)" and "Stop and report when"; the return contract (status, commits, one test line, concerns; the report is a file); model classes A to D with every dispatch naming its model; a feasibility probe before briefs; ordered attack questions for full-tier QA; "Steps to verify" in implementer reports; "Verified" and "Not verified" in the controller's status; a Known hazards list in the hand-off template.
- **Seed rulings** K34 to K44 record the new rules with their reasons and supersede K1, K13, K18 and K21 by name.

Design choices, each with its reason:

- The rules file is ordered by audience and each role stops where its part ends, because one file read in part is cheaper than three files that restate each other. Hard rules 21 to 23 (merges one at a time, never force-remove a worktree that holds work, rulings are never rewritten) were stated only in the playbooks and are numbered now.
- A seed ruling whose rule is in the rules file names it and keeps only the reason and how to apply it; a superseded one keeps its own words, because a K number must not change its meaning.
- The tier lives in the status record on main, not only in the SPEC, because the gates must read it from somewhere a branch cannot write, and a fast-path task has no SPEC.
- Lower tiers are off until `tiers.full_paths` in `program/checks.yaml` lists the full-tier paths, so an upgraded program behaves exactly as before and "unsure" means full.
- Full-tier work is named by path, because a script can check a path and cannot check an intention; `kit/`, `program/checks.yaml` and `program/gates.yaml` are always full.
- A light task ends at `merged`, not `done`, so hard rule 6 holds as written: `done` still means QA accepted it with evidence. A `merged` task evidences nothing in a gate claim.
- The light gate keeps the scans, because a secret can land in any file; `--inspected <sha>` must name the branch tip, so the controller's diff inspection is a recorded statement about one commit.
- The standard tier keeps the hand-back gate and the evidence record unchanged and saves only QA's re-run and planted-bug quota (the suite runs twice, not three times), so the evidence model is untouched.
- The fast-path brief is held to what a SPEC and PLAN are held to (on main, unchanged by the branch, required sections), and a fast-path task cannot change a guarded file, because the approval line lives in a SPEC.
- An ad-hoc task's tracking state ends at `closed`, not `done`, so `done` stays a word only QA can write; `closed` is refused while its status record is in flight.
- Any tag defers a follow-up (counted by tag, not listed), because the only use of a tag so far is "not until that task resumes".
- `pk record` requires a ruling, validates everything it can before it writes, runs only on main with nothing staged (with `--no-commit` too), and takes the attribution line as `--trailer`, because a script cannot know who is typing (hard rule 16). A write or a commit that fails puts its three files back. The size budget can only be measured on the rewritten hand-off, so a step that goes over it is committed and then exits 1 with the reason.
- The fresh-agent threshold is 400,000 tokens or three resumes per agent of a task, overridable on `pk cost report`; `--agent` labels one session so its resumes add up.
- The hand-off budget is 60 KB (override: `pk record --handoff-budget BYTES`, so a raise carries a ruling; it is stored as `handoff_budget_bytes` in the controller state and stated in the generated block) and Next steps 2 KB; the rulings window is one clipped line per ruling, because the full text is one command away.
- A full-tier task is never a member of an integration round, and a round's re-check is the whole suite once, because a script cannot choose a safe subset of tests.
- `pk merge` runs `git merge` itself, for one task, and refuses a branch that is not accepted: the kit now refuses to merge unaccepted work, which 0.2 left to the controller. "Accepted" is derived, as `pk status set done` derives it, from the evidence committed at the branch tip; the word `done` in the status file is necessary and not sufficient.
- The acceptance binds the reviewed commit (the `head` of the accepted results record). After it a branch may add only its status file `program/status/<ID>.json`, under `program/evidence/<ID>/` only `latest.json`, `report.md` and records directly in `results/` and `acceptance/` (what the kit and the implementer's report write; a record must carry a record name and the evidence at the tip must pass the store's integrity check, as `pk evidence validate` runs it), and clean merges of main; any other file in the evidence folder, in `results/` and `acceptance/` too (`produce.py`, a `conftest.py`, a test file a runner would collect), is refused like any other late change; a later commit that changes anything else, a revert included, and a merge commit that is not what git makes of its two parents are refused, because nobody reviewed them. The way on is the ordinary one: the gate runs on the new tip, the reviewer is moved to it (`pk worktree review` again) and QA accepts that record.
- `merged` is audited like `done`. The record stores the inspected commit; `pk status set <ID> merged` without `--inspected` is refused; setting it and `pk status validate` both require main to hold a merge of exactly that commit, the task to have been light on main when it landed, and the light path's guard to pass again on what the merge brought in (`<merge>^1..<merge>`, so a file added inside a hand-made merge commit counts). While `task/<ID>` exists, `--inspected` must be its tip. The check works from the merge commit, so it holds after the branch is deleted.
- A full-tier `done` needs an acceptance that lists the commands QA re-ran and at least three planted bugs of its own, so the two depths of the QA brief leave different records. A status record written before tiers existed is not held to it afterwards. Whether the quota applies is read from main's record, never from the branch's, and a branch whose status file drops the `tier` field main's record names changes its tier and fails the gates, so a new task cannot claim that exemption.
- `pk worktree finish --compose-project NAME` selects containers and volumes by the label `com.docker.compose.project=NAME`, which the container tool matches exactly, and never by a name prefix: a name prefix reaches `NAME-dev` and `NAME_e2e`, which are other projects. Images are not removed at all: a label is not reliably on them, a name is the only other handle, and they are rebuilt from the repository. Each thing is removed by its own name, one at a time and without `-f`. Every check and both listings come before the first removal; it refuses an unmerged branch unless `--keep-branch`, a worktree standing on a commit no branch holds, and git-ignored files unless `--drop-ignored`.
- QA reviews in a detached worktree but commits its acceptance on the task branch, so the acceptance still binds the task's latest results record and nothing about `done` changed. The implementer stops when it hands back, as in 0.2: the review worktree exists so that reviews of several tasks run at once and a reviewer's planted bugs never touch the task worktree, not so that the branch can move under the reviewer.
- The kit still names no model: classes A to D are roles, the mapping is the program's (`program/COMMON.md`), and `pk cost add` refuses a run without a model.
- The feasibility probe, steps to verify, verified and not verified, and batched user decisions are rules, brief sections and templates only: none of them relaxes a check, so none needs a gate. Contract first has one check: the contract goes to main with the definition, and the gates hold a branch's copy identical to main's.
- The fast brief is checked as written: its four sections, and a `Tier:` and a `Ruling:` line equal to the status record. A tier is held to the record's own history (the dispatch entry names it, each change names its ruling), so a tier edited by hand does not validate.
- A `tiers` path covers everything under it with or without its trailing slash, and `pk doctor` warns about an entry that covers no tracked file.
- `pk record`, `pk merge` and `pk rulings validate` refuse a rulings log that no longer begins with the bytes committed at HEAD (hard rule 23), so no command of the kit commits a rewritten ruling.
- A round record is re-derived from git when a member lands and when the round closes, so a record written by hand that does not describe `round/<NAME>` covers nothing. That fixes L11 in part: the record cannot prove that `pk integrate check` ran (see Known limits).
- No dashboard: the generated hand-off block is the kit's view of the state.

Upgrading a 0.2.0 program:

1. `sh install.sh /path/to/your-repo --upgrade`. Status records without a tier read as `full`; a 0.2 `controller-state.json` reads as it is and gets follow-up IDs the first time a command writes it; evidence is untouched.
2. Copy `kit/templates/COMMON.md` to `program/COMMON.md` and fill it in.
3. On main, add a `tiers` section to `program/checks.yaml` (copy it from `kit/templates/checks.yaml`) and list your full-tier paths. Leave it empty to keep every task full.
4. Replace references to the three old rule files with `kit/rules/RULES.md` in your hand-off, and add a Known hazards section if you want the seeded list.
5. Run `pk handoff update` and `pk handoff check`. If the check fails on the size budget, move history into rulings and close or tag follow-ups; `handoff_budget_bytes` raises the budget meanwhile.
6. Scripts that parsed `pk status list` get a fifth column (the tier); `pk status set` prints the tier when it is not full. `pk trace impact` and `pk change impact` gain a `merged` bucket.

Known limits:

- A hand edit that rewrites a status record's tier and the dispatch entry of its history together, or the `Tier:` line of a SPEC on main, is not detected by a script: the spec-QA record does not bind the SPEC's bytes, and the audit is main's git history (review finding L6, in part).
- A ruling is checked for existence only. Any existing ruling allows a fast path or a tier change; nothing requires its text to name the task, because one ruling may cover a class of tasks (L17, in part).
- `pk integrate close --recheck` does not drop a member that never merged: a round with such a member stays open, and is shown as open in the hand-off. The branch `round/<NAME>` of a closed round stays among the unmerged branches, because it names the tested tree (L12, in part).
- `pk record` puts its files back when a write or the commit fails; a process killed between the writes is not undone (`git status` shows the three files) (L16, in part).
- The model mapping table of `program/COMMON.md` is not checked: it ships blank, `pk doctor` does not warn about an empty cell and `pk cost add` takes any model name. A check would make `pk doctor` warn on every fresh install (L20, in part).
- Decisions the user owes have no list of their own: one a task waits on is that task's parked note, shown in the hand-off, and any other is a follow-up with the area `needs user` (L20, in part).
- The removals of `pk worktree finish --compose-project` are tested against a stand-in container tool. Only the listing was tried against a real one, read-only: its label filter matched a value exactly and not by prefix.
- A follow-up removed from the controller state together with a matching edit of `followups_issued` is not detected; the audit is git history.
- After `task/<ID>` is deleted, nothing ties a `merged` record's inspected commit to the task: a record set or written then may name a decoy, a light-only merge of another commit (or the branch's own first commit merged on its own), and the audit then checks that merge, not the task's work (re-review N1).
- A started round's record with the correct tested tree typed into it (the tree of `round/<NAME>`) passes the re-derivation, and its members land through `pk merge --round` with no suite run: nothing short of a signed or recomputed result can show that `pk integrate check` ran (re-review N4; L11 in part).
- QA's check that the branch tip is the commit it reviewed is in the QA brief only (`qa.md` step 7). After the review, a late commit followed by a re-run of `produce.py` and a commit of its new record moves the record's `head` to the late commit; if QA accepts that record without the tip check, `pk merge` lands the late commit, which no reviewer's diff showed (re-review N5).
- Seed ruling K18 keeps the words "Tier 1, Tier 2" for model strength, marked superseded by K35: a K number does not change its text.

## 0.2.0

Breaking change: the evidence layout.

- **In-repo, append-only records.** A task's evidence is no longer one `program/evidence/<ID>/results.json` and one `acceptance.json` rewritten in place. Each run appends a new, read-only record named by its own digest, `program/evidence/<ID>/results/<utc>-<sha256[:12]>.json` (QA's acceptances under `acceptance/`), and records are never modified or deleted (rule 11). Each task's pointer `program/evidence/<ID>/latest.json` names its latest results and acceptance record and is the only mutable evidence file; a task branch edits only its own pointer, so evidence never conflicts on merge. `pk evidence validate` with no record, the hand-back gate and `pk doctor` refuse a record whose bytes no longer match its name, a commit (merge commits included) that modified or deleted a record, a pointer that does not name its task's newest record, and a pointer entry that does not resolve to a committed record. `pk evidence history <ID>` lists every record of a task. A refresh appends a record with `supersedes`; a re-acceptance appends an acceptance (`pk evidence accept`).
- **Drift replaces staleness.** A record states what was verified at its `head` and stays true; a later change only makes it drift. `pk stale` is now a drift report (`fresh` or `drifted since <head>`, against the checkout's HEAD) that exits 0 unless `--strict`. Records no longer carry a `stale` field and `Evidence.stale()` is gone. The hand-back gate asks a task for a new record only when its own inputs changed; `pk gate binding` reports drift instead of failing on it; `done` needs the latest acceptance to bind the latest results record and its head to be an ancestor of HEAD. A gate record binds its children by digest and records each child's drift.
- **Acyclic closure.** A record binds only inputs, never a derived output (rule 12). `pk evidence lint` names offending inputs; `Evidence.write`, the gate, the binding check and `done` refuse them. Only a gate record binds other records, by digest; nothing binds a gate record.
- **API.** `Evidence.write()` takes no path and returns `{digest, path, file}`. New commands: `pk evidence lint`, `history`, `accept`, `import` and `validate` with no record (`init` creates nothing); `pk stale --strict`. `pk doctor` runs the evidence integrity checks and warns about a record pending commit.
- **Import path for 0.1 projects.** Run `pk evidence import`: it copies each `results.json` and `acceptance.json` byte for byte into the new layout as the first history entry, writes each task's pointer, and prints the exact `git rm` lines for the originals (it never deletes them). `gates.yaml` records may keep `path: program/evidence/<ID>/results.json` or say `task: <ID>`.
