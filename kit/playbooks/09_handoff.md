# Playbook 09: hand-off and takeover

## Purpose

Keep one document, `program/HANDOFF.md`, current and small enough that a different agent, model or provider can read it whole and take over at any moment, and give that successor a prompt that starts it correctly. Use this playbook when you stop, when you resume after a break, and when you take over from someone else.

## Inputs

- `program/HANDOFF.md`: a maintained part, one headed section each for how the program works, environment setup, known hazards, next steps and where the rules live, and a part generated by `pk handoff update`: the Now list (the controller's one line, every task in flight with its tier and what a blocked one waits on, open ad-hoc tasks, open integration rounds), counts (done tasks by tier), unmerged branches and worktrees, queued and parked tasks (a parked one with the decision it waits on), open follow-ups, open change requests, agents past the fresh-agent threshold and the newest fifteen rulings with the next free number.
- `program/controller-state.json` (written by `pk record`, `pk followups` and `pk adhoc`, never by hand: `pk record` has a flag for each thing the hand-off shows, `--now`, `--note <ID>=TEXT`, `--queued`, `--parked` and `--handoff-budget`), `program/rulings.md`, `program/costs.jsonl`, `program/COMMON.md`.

What each role reads at start, and nothing more. Sizes are the kit's files as shipped; `program/COMMON.md` is counted as its template.

| Role | Reads at start | Kit files, KB |
|---|---|---|
| Controller or successor | `program/HANDOFF.md` (60 KB at most), `kit/rules/RULES.md` whole, `kit/briefs/controller.md`, `kit/playbooks/00_START.md`, `kit/playbooks/08_execute.md`, `program/COMMON.md` | 48.5 |
| Implementer, full or standard tier | `kit/rules/RULES.md` parts 1 to 3, `kit/briefs/implementer.md`, `program/COMMON.md`, the task's definition | 19.5 |
| Implementer, light tier | `kit/rules/RULES.md` parts 1 and 2, `kit/briefs/implementer.md`, `program/COMMON.md`, the task's definition (the fast-path `BRIEF.md`, or its SPEC and PLAN) | 13.7 |
| QA | `kit/rules/RULES.md` parts 1 to 3, `kit/briefs/qa.md`, `program/COMMON.md`, the task's definition, the diff file and the stat file | 20.4 |
| Spec QA | `kit/rules/RULES.md` parts 1 and 2, `kit/briefs/spec_qa.md`, `program/COMMON.md`, the SPEC and PLAN | 12.7 |

Rulings are read by number when something cites one (`program/rulings.md`, `kit/rules/RULINGS_SEED.md`), never top to bottom. No role reads another role's brief.

## Steps

1. Outgoing controller: finish or park the step you are on. Void any partial evidence by exact path. Leave no dirty worktree, and run `pk worktree finish <ID>` for each merged task.
2. Update the maintained sections of `program/HANDOFF.md`: how the program works, current environment setup, any hazard met twice under Known hazards, and under Next steps only the order of what comes next (2 KB at most; the generated Now list says what is in flight). Where the rules live stays one line. The hand-off carries state, not rules and not history: a decision goes in a ruling (`pk record --ruling TEXT`), and a ruling that changes the process changes the playbook or rule file in the same commit. Keep the model mapping in `program/COMMON.md`.
3. Run `pk handoff update`, then `pk handoff check`. It exits 1 while the generated part is stale, while the file is over its budget (60 KB) or while Next steps is over 2 KB. When over budget: close or tag follow-ups (`pk followups close`, `pk followups tag`), move history into rulings, trim the hand-written sections; if it must be raised meanwhile, `pk record --ruling TEXT --handoff-budget BYTES` does it by a ruling and the hand-off then says so. Commit `program/` only when it exits 0.
4. Give the successor the prompt below, and tell the user who is taking over.
5. Successor: follow the prompt. Do the state check before anything else. Write your own model mapping into `program/COMMON.md`, and use your own attribution line on commits.
6. A successor never restarts an accepted task and never resumes an agent whose task has since merged.

## Successor prompt

Give everything in this block to the agent that takes over.

```
You are taking over as controller of a governed software delivery program in this
repository. Another agent ran it until now. Keep delivering the remaining tasks to main
at the same quality bar, with the least rework. All state is in the repository, and the
rules are in one file.

1. Read program/HANDOFF.md top to bottom, kit/rules/RULES.md (all four parts),
   kit/briefs/controller.md and program/COMMON.md. Read rulings by number only.
2. Verify the state before you act:
   - git status on main, git branch --no-merged main and pk worktree list; compare
     with HANDOFF. In each worktree run git status --short: a modified or untracked
     evidence record, pointer or claim file is void partial evidence (delete the record
     by literal path, restore the pointer with git checkout -- <path>; never commit it).
   - Leftover processes, containers and ports this program started, and free disk
     space. Touch only what is ours, by exact name.
   - pk fetch --pins <file.json> in the background, if the project has pins.
   - The repo-wide suite passes on main: run the test commands of program/checks.yaml
     on a clean checkout. If it fails, stop and tell the user before you dispatch.
   - pk handoff check. If stale, run pk handoff update and commit.
3. Tell the user in a few lines what you found, what you verified yourself and what
   you will do next.
4. Resume at the Now list and Next steps of HANDOFF, following
   kit/playbooks/08_execute.md. The hard rules of RULES.md part 1 bind you from the
   first command.
```

## Outputs

A current `program/HANDOFF.md` within its budget, a committed `program/`, the successor prompt delivered, and the model mapping recorded in `program/COMMON.md`.

## Done when

`pk handoff check` exits 0, the working tree and every task worktree are clean or hold only voided partial evidence you have named, and the successor has confirmed the state check.
