# Playbook 09: hand-off and takeover

## Purpose

Keep one document, `program/HANDOFF.md`, current enough that a different agent, model or provider can take over at any moment, and give that successor a prompt that starts it correctly. Use this playbook when you stop, when you resume after a break, and when you take over from someone else.

## Inputs

- `program/HANDOFF.md`: a maintained part, one headed section each for how the program works, environment setup, known gotchas, next steps (ordered), where the rules live (one line) and model tiers, and a part generated by `pk handoff update` (counts, in-flight tasks, unmerged branches and worktrees, queued and parked tasks, open follow-ups, open change requests).
- `program/controller-state.json`, `program/progress.md`, `program/rulings.md`, `kit/briefs/`.

## Steps

1. Outgoing controller: finish or park the step you are on. Void any partial evidence by exact path. Leave no dirty worktree.
2. Update the maintained sections of `program/HANDOFF.md` (they start empty): how the program works, current environment setup, new gotchas and the ordered next steps. Keep one line under Where the rules live that names `kit/rules/HARD_RULES.md`, `EVIDENCE_HONESTY.md`, `THROUGHPUT.md` and `program/rulings.md`. HANDOFF carries state, not rules. Record your model-tier mapping under Model tiers (which model you used as Tier 1, which as Tier 2, or that you had one model). A ruling that changes the process changes the playbook or rule file in the same commit.
3. Run `pk handoff update`, then `pk handoff check`. It exits 1 while the generated part is stale. Commit `program/` only when it exits 0.
4. Give the successor the prompt below, and tell the user who is taking over.
5. Successor: follow the prompt. Do the state check before anything else. Record your own tier mapping in HANDOFF, and use your own attribution line on commits.
6. A successor never restarts an accepted task and never resumes an agent whose task has since merged.

## Successor prompt

Give everything in this block to the agent that takes over.

```
You are taking over as controller of a governed software delivery program in this
repository. Another agent ran it until now. Keep delivering the remaining tasks to main
at the same quality bar, with the least rework. All state is in the repository.

1. Read program/HANDOFF.md top to bottom. Then read kit/briefs/controller.md,
   implementer.md, qa.md and spec_qa.md. Read kit/rules/HARD_RULES.md,
   EVIDENCE_HONESTY.md and THROUGHPUT.md. Read program/rulings.md and
   kit/rules/RULINGS_SEED.md only by heading, for the rulings a SPEC or report cites.
2. Verify the state before you act:
   - git status on main, and git branch --no-merged main; compare with HANDOFF.
   - pk worktree list.
     In each worktree run git status --short. A modified or
     untracked evidence record, a modified program/evidence/<ID>/latest.json or claim file
     is void partial evidence: delete the record by literal path and restore the
     pointer or claim file by exact path (git checkout -- <path>). Never commit it.
     Never edit or delete a committed record. Never force-remove a dirty worktree.
   - Look for leftover processes and containers that this program started, and check
     free disk space. Touch only what is ours, by exact name.
   - Run pk fetch --pins <file.json> in the background once per host, if the project
     has pins, so no gate step waits on a download.
   - Check that the repo-wide suite passes on main: run the test commands in
     program/checks.yaml on a clean checkout of main. If the suite fails on main,
     stop and tell the user before you dispatch anything.
   - Run pk handoff check. If it exits 1, run pk handoff update and commit.
3. Tell the user in a few lines what you found and what you will do next.
4. Choose your tiers. Tier 1 is your most capable model: you as controller,
   first-pass implementation, first-pass QA, specs. Tier 2 is a cheaper model, for
   scoped re-checks of exact fixes, mechanical re-runs and resume-only work, and it
   must report ESCALATE rather than accept anything outside its checklist. With one
   capable model, use it for everything. Write your mapping into HANDOFF.
5. Resume at HANDOFF's next steps, in order, following kit/playbooks/08_execute.md.
   Never restart an accepted task. Never resume an agent whose task has since merged.
6. Keep the rules: never fabricate evidence; never claim an environment that does not
   exist; only QA sets done; never rewrite history; never push or deploy unless the
   user says so; surface any denied action to the user. End your commits with your
   own attribution line.
```

## Outputs

A current `program/HANDOFF.md` with the generated part fresh, a committed `program/`, the successor prompt delivered, and your tier mapping recorded.

## Done when

`pk handoff check` exits 0, the working tree and every task worktree are clean or hold only voided partial evidence you have named, and the successor has confirmed the state check.
