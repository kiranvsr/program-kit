# Rules

The one rules file of the kit: everything else points here. If a rule seems to block the work, stop and tell the user. Do not look for a way around it.

Read top to bottom and stop where your part ends. Every agent: parts 1 and 2. Implementer and QA of a full-tier or standard-tier task: also part 3. Controller: all four. Cite a rule as `hard rule 6`, `working rule W3`, `evidence rule 11` or `controller rule C2`.

## Part 1. Hard rules (every agent, every role, every stage)

### Evidence and claims

1. Never fabricate evidence, test results, CI results, gate passes or human approvals.
2. Never claim anything about an environment that `program/environments.yaml` marks `exists: false`. Work that needs one stays `blocked_by` that environment.
3. Development acceptance is not production readiness. Say "accepted for development" and nothing stronger.
4. An acceptance lives where the code reads it. A side file that leaves the fields the code reads unaccepted is not an acceptance. Accept in the file the reader reads.
5. Run the checks and evidence commands from a clean tree. The project must git-ignore the bytecode and build output its test and scan commands write (`__pycache__`, `*.pyc`, `dist/`, `target/`, `node_modules/` and the like). If it does not, an untracked leftover makes the clean-tree check fail. Add the pattern to `.gitignore` before you start.

### Status, register and frozen artifacts

6. Only QA sets a task `done`, and only through `pk status set <ID> done --role qa`, after `pk evidence accept` appended an acceptance of the latest results record.
7. Record every register edit with `pk register change --note TEXT`, or with `pk change apply CR-NNN --note TEXT` when the edit carries out an approved change request. Never hand-edit status files, approvals or generated briefs.
8. Briefs are immutable once approved.
9. A frozen artifact (anything approved at stage 5 or later) changes only through a change request. See `kit/playbooks/10_change.md`.
10. Guarded files (the `guarded_files` list in `program/checks.yaml`: build files, CI definitions, dependency manifests) change only with the user's approval. The approval is a `Guarded edit: <path>` line in the task's SPEC on main, written before dispatch. A branch cannot approve its own edit.

### Git and files

11. Never rewrite history: no rebase, no reset, no force-push. Merge main into your branch with a merge commit.
12. Never use a bare `git stash`.
13. Never commit secrets, private keys, or any artifact whose licence the project lists as restricted.
14. Never push, deploy or apply infrastructure unless the user explicitly tells you to.
15. Every destructive command uses a literal path. No variables, no globs, no recursive prune of shared resources. Clean up only what you created, by its exact name.
16. Commit messages end with your own attribution line, not one copied from a brief or an earlier commit.
17. Never commit editor, operating-system or build leftovers, or scratch files.

### Permissions and scope

18. If an action is denied, stop and report it to the user. Never route around a denial, and never ask another agent to do what was denied.
19. Ask the controller only in the four NEEDS_CONTEXT cases: a new dependency; a security boundary with no precedent; a change to user scope; two conflicting rulings. Decide everything else yourself and record the decision.
20. Build exactly the scope in the task's SPEC and PLAN. Anything outside it is a follow-up, not an edit.

### Merges, worktrees and rulings

21. Accepted branches merge into main one at a time. Work may be dispatched in parallel; merges never are.
22. Never force-remove a worktree that holds work. A task or review worktree with uncommitted or untracked files is removed only after its owner has committed or deleted them by exact path.
23. A ruling is never rewritten, renumbered or deleted. A later ruling supersedes an earlier one by name.

## Part 2. Working rules (every agent)

- **W1. Decide, don't ask.** Anything with precedent is decided by the agent and recorded as a deviation citing the precedent. Questions go to the controller only in the four NEEDS_CONTEXT cases of hard rule 19; the controller answers with a numbered ruling.
- **W2. A gate passes on its OK line.** The implementer runs `pk gate handback <ID> --branch task/<ID>` before any QA round; a hand-back that fails the gate returns without one. Exit code 0 alone is never accepted: read the last line.
- **W3. Fix rounds and scoped re-checks.** QA numbers its findings, each with severity, location and the exact fix. The same implementer, resumed, fixes them and returns a finding-to-fix table: finding, fix, commit, command that shows it fixed. The same reviewer, resumed, re-checks only those findings and the binding. The implementer re-runs the hand-back gate after the fix; QA never does.
- **W4. Your own folder, your own worktree.** Scratch files go only in a folder named for your task and role; delete only those, by exact path. Before a command that commits or deletes, check where you are (`git rev-parse --show-toplevel`): a shell that drifted into another worktree commits to the wrong branch.
- **W5. No polling.** Run long commands in the background with output redirected to a file, and wait for completion. Never use sleep loops and never `tail -f`.
- **W6. The return contract.** Your final message is four things: status, commits, one line of test results, concerns. The full report is a file, under your brief's fixed headings and under 25 lines; the message names its path. Never paste a diff, a log or a SPEC into a message.
- **W7. Read only what you are pointed at.** Your parts of this file, `program/COMMON.md`, your brief, your task's definition and the rulings it cites, by number. Not the ruling log, the hand-off or another role's brief.
- **W8. Interruptions.** After a session or rate limit, void partial evidence by exact path, then resume at the interrupted step: resume from the last commit, re-run only the interrupted step. Never restart a task from scratch.
- **W9. Decided means decided.** What your definition lists under "Decided (do not reopen)" is not yours to revisit. When a "Stop and report when" condition occurs, stop and report; do not work round it.
- **W10. Work to your tier.** Your task's verification tier is in its status record (`pk status show <ID>`). Do what it asks, no less and no more, and never change it. If the work turns out to touch a full-tier path, stop and report: the controller raises the tier by a ruling.
- **W11. Report the cost.** End your report with a Cost line: model, tokens, tool calls, seconds, resumes, as far as your tooling shows them.
- **W12. Fast default, slow set in the release set.** The `test` step of `checks.yaml` is the suite that finishes in minutes and runs at every gate and merge check. Cases that build whole fixtures or spawn many processes sit behind one environment variable the project names (`<PROJECT>_TESTS_SLOW=1`), are skipped by default, and run in their own tracks of `program/release-set.yaml`. A thirty-minute suite at every hand-back makes agents skip it or wait on it; `pk fingerprint run` runs it in parallel once per commit that matters.

## Part 3. Evidence honesty (implementer and QA of a task that produces evidence)

Evidence is a record that something was run and what really happened. It is worth something only if it cannot flatter the work. The hand-back gate checks the mechanical ones (literal PLAN commands, a clean tree, one-commit binding, commands as expected, planted bugs killed, intact record history, no derived output bound). QA checks all twelve. A task that breaks one is returned without a QA round.

1. **Run PLAN commands literally, exactly as written.** Why: a substitute (`true`, an extra flag, a narrower path) proves a different thing from the one the PLAN promised. If a command cannot run as written, fix the code or record a named deviation. Never substitute.
2. **Parse every derived field from real output and assert it.** Never write "unparseable" or "unknown" in a run marked as expected. Why: a field nobody checked is a claim nobody made.
3. **Give every new guard a cheapest-defeat planted bug that the gate's own test catches.** The cheapest defeat is the smallest edit that disables the guard (dead code, a comment, a copied field, a pass-through). Why: a guard whose removal changes nothing is decoration.
4. **A planted bug counts only when a test fails.** A build failure or a setup failure is not a catch, and planted bugs must build. Each row of the planted-bug runner records the file, the edit and the build and test commands, so a reviewer sees what was planted and what judged it without reading the producer. Why: otherwise a typo "catches" every bug and the table proves nothing.
5. **Test every new access policy across its boundary** (tenancy, roles, permissions, row filters). Use an eligible-record positive control (the owner can read and change it), a cross-boundary negative (another principal cannot), and a planted wide-open policy that the test must catch. Why: a denial test with no eligible record passes even when the data is unreachable for every reason.
6. **Hash complete consumed inputs.** Hash unchanged source, tests, fixtures, the dependency closure, generated-file sources, migrations, tool helpers, config and lock files, not only the files you changed. Why: stale detection can only see what was hashed.
7. **Produce evidence only from a clean tree, bound to one commit.** Never hand-edit a hash or the recorded commit: `pk gate binding` recomputes every recorded hash at the recorded commit and refuses a record whose commit is not an ancestor of the branch tip. Why: a hash edited by hand is a forgery, and an unclean tree makes the bound commit a lie.
8. **Void partial evidence by exact path before you resume.** Why: a half-written record from an interrupted run looks like a real one.
9. **When you refresh an older record, re-run every command it holds and append a new record with the real result of each.** Never drop an entry and never keep an old number. A claim whose output changed is rewritten, in the new record, to what the command now proves. The new record names the one it replaces (`supersedes`); the older one stays in the history untouched. Why: a refresh that keeps old numbers turns a snapshot into a rumour, and one that overwrites the old record erases what was once claimed.
10. **Validators and gate steps never download inline.** Anything fetched (toolchains, pinned archives, fixtures) is cached by content digest in a durable per-host cache, fetched once per host by the separate `pk fetch` step run in the background at session setup, and verified locally against the recorded digest. A verify step that finds its input missing fails and prints the fetch command to run. It never downloads. The fetch step validates every cached name against a strict pattern, writes through an exclusively created temporary file in the cache directory, removes it on any failure, checks size and digest before the rename, and never follows a symlink for a cache entry or its parent. Each of those guards has its own test and planted bug. Why: a gate that waits on the network is slow and flaky, and a download inside a check can change what is being checked.
11. **Evidence records are committed, append-only and immutable: a record file is never modified or deleted once committed; the per-task latest.json is the only mutable evidence file.** A record lives at `program/evidence/<ID>/results/` or `acceptance/`, named `<utc>-<sha256[:12]>.json` after its own bytes; each task's `program/evidence/<ID>/latest.json` names its latest record. `pk evidence validate`, the hand-back gate and `pk doctor` refuse a record whose bytes no longer match its name and a commit that modified or deleted one. A later change never makes a record stale: it records what was verified at its `head`, and `pk stale` only reports drift from the tree at the checkout's HEAD. Why: a record that can be rewritten proves nothing, and a record that goes stale whenever anything moves turns every merge into a re-bind.
12. **A record binds only its inputs, never a derived output.** Never hash another record, an acceptance, a gate result, a status snapshot, an approval or the register change log, a generated claim document, or anything under `program/evidence/` other than the producer and its tooling (`*.py`, `*.sh`, `*.toml`). Only a gate record binds other records, by digest, and nothing binds a gate record. `pk evidence lint` names an offending input as `binds a derived output: <path>`; the evidence writer, the gate, the binding check and `done` refuse it. The interview's requirements ledger (`program/ledger.yaml`) is an input, not a derived output. Why: a record that binds its own outputs goes stale the moment it is accepted, and the evidence graph becomes a cycle no refresh can close.

## Part 4. The controller's rules

- **C1. Merge queue.** Work is dispatched in parallel and merged one at a time (hard rule 21). QA starts once a branch's evidence reflects current main, and may run on several branches at once, each reviewer in its own review worktree (`pk worktree review <ID>`). Accepted branches merge in the order they were accepted; a documentation-only hand-off commit may land in between.
- **C2. A main move does not start a re-bind.** If main moved without touching a branch's own hashed inputs and `git merge-tree --write-tree main <branch>` is clean, the branch does not re-merge or re-produce its evidence. Any overlap means merge main, re-run the gate (it appends a new record when the task's own inputs changed), then QA. A record never goes stale: `pk stale` reports drift for the reader, and each task refreshes only its own record, by appending one, when its own work changes.
- **C3. The merge check is the controller's own gate run.** `pk merge <ID>` lands one task: it refuses a branch QA has not accepted, runs `pk gate merge-check` without relying on the implementer's run (guarded files, tier, the task's definition, then build, tests and scans on a trial merge), merges, rewrites the claims, regenerates the hand-off and commits the bookkeeping. "Accepted" is derived from the evidence committed at the branch tip, as `pk status set <ID> done` derives it: the word `done` in a status file is not enough. The acceptance binds the reviewed commit: after it a branch adds only `program/status/<ID>.json`, under `program/evidence/<ID>/` only `latest.json`, `report.md` and records directly in `results/` and `acceptance/` (named `<utc>-<sha256[:12]>.json`, their bytes hashing to that name), and clean merges of main; anything else, a `produce.py`, `conftest.py` or test file anywhere in the evidence folder included, is refused until the gate ran on it and QA accepted that record. A branch whose implementer skipped the gate cannot reach main.
- **C4. Model classes, and always name the model.** Four classes, by role. Class A, the most capable model you have: the final review and QA of a full-tier task, any security ruling, and design where the unknowns are real. Class B, a strong model: the controller, specs and spec review, the interviewer and lens rounds, and implementation that crosses a security or integration boundary. Class C, the floor for judgement: first-pass implementation, the scoped review of a standard-tier task, and fix rounds. Class D, the cheapest: mechanical re-runs with a checklist, the feasibility probe and resume-only work; it reports ESCALATE for anything outside its checklist and never accepts on judgement. Never below class C for first-pass work, and never below class A for accepting a full-tier task with an open important finding. With fewer models, one model fills several classes. `program/COMMON.md` maps each class to a model by name, every dispatch names its model, and `pk cost add` refuses a run without one.
- **C5. Concurrency.** At most three implementers and four agents at once (implementers, fix rounds and QA together). Work closest to merge goes first. Never resume an agent whose task has since merged.
- **C6. Fetch once.** Run `pk fetch` in the background once per host at session setup, so no gate step ever waits on a download.
- **C7. Repeated rejections become a gate rule.** When two rejections share a cause, stop fixing task by task: add the cause as a check in the hand-back gate (a command in `extra_gate` in `program/checks.yaml`, or a new step in the gate), and record a ruling.
- **C8. Gates on a quiet main.** A gate that reads every record (a phase gate, a re-bind batch) is voided by any merge. Merge the feature tasks first, then run the gates back to back on a quiet main, merging each result before the next gate starts.
- **C9. Controller commits.** Record a step with `pk record`: the ruling, the state change, the hand-off and one commit of exactly those files. Commit hand-off and controller-state updates only after a merge, a ruling or at session end; evidence closures exclude them. The one exception is the dispatch commit: a task's definition (SPEC, PLAN and spec-QA review, or the fast-path BRIEF) and its `in_progress` status go to main together, as one commit, before its worktree is created, because the gate reads them from main. After that the status record changes on the task branch, with two exceptions the controller makes on main: a tier change (`pk status tier`; the branch then merges main and takes main's record) and the `merged` record of a light task, which `pk merge` writes. A generator never changes a tracked file it does not name: after `pk handoff update` on a clean tree, `git status` shows `program/HANDOFF.md` or nothing.
- **C10. Main must be green.** A successor verifies that the repo-wide suite passes on main before it dispatches anything.
- **C11. Verification tiers.** Every task has a tier, chosen when it is specified, recorded at dispatch (`pk status set <ID> in_progress --role controller --tier <tier>`) and changed only by a ruling (`pk status tier`). Full is the default and the answer whenever you are unsure.

  | Tier | For | The process | Ends at |
  |---|---|---|---|
  | `full` | anything touching access control, tenancy, data migrations, cryptography, release or the kit's own gates | everything: spec QA, the hand-back gate, QA that re-runs the PLAN commands, plants at least three bugs of its own and works through the attack questions, then the merge check | `done`, set by QA |
  | `standard` | ordinary product work off the full-tier paths | tests plus one independent scoped review: the suite runs once at the hand-back gate and once at the merge check; QA checks the binding and reviews the diff against the SPEC, with no planted-bug quota and no re-run | `done`, set by QA |
  | `light` | the kinds of change a ruling of this program names (`tiers.light_ruling`, `tiers.light_paths`) | the build, the compile check and the scans, then the controller reads the diff (`--inspected <sha>`); no tests, no evidence, no QA | `merged`, set by the controller; never `done` |

  The gates enforce the tier from main: the lower tiers exist only once `tiers.full_paths` in `program/checks.yaml` lists the program's full-tier paths, and a task below full that changes one of them, or a light task that leaves the light paths, fails. A `merged` task evidences nothing in a gate claim. Its record names the commit the controller inspected, and `pk status validate` checks it as it checks `done`: main holds a merge of exactly that commit, the task was light when it landed, and the merge brought in no full-tier path and nothing outside the light paths.
- **C12. The fast path.** For small bounded work the user asks for directly: one `program/tasks/<ID>/BRIEF.md` and a ruling replace SPEC, PLAN and spec QA (`--fast --ruling R<n>`). It is never available for the full tier; the status machine and both gates refuse it. Work outside the register is an ad-hoc task (`pk adhoc add`), tracked in the hand-off like a register task.
- **C13. Integration round.** Several accepted branches below the full tier may be verified together: `pk integrate start`, one combined check and acceptance round on the combined tree (`pk integrate check`), then `pk merge <ID> --round <NAME>` one at a time, then `pk integrate close`, which compares the tested tree with main. Anything changed since is re-checked before the round closes. A full-tier task is never a member.
- **C14. Contract first.** Work with a server part and a client part has its interface written first (`program/tasks/<ID>/CONTRACT.md`, from the template). It is part of the definition: the controller commits it to main in the dispatch commit, where every worktree sees it, and both parts build against it in parallel. A branch never edits it (the gates hold it identical to main's); a change is appended on main by the controller, with its reason, never edited in.
- **C15. Dispatch hygiene.** A brief points to `program/COMMON.md` and never repeats it. It states what is already decided, when to stop and report, the return contract and the model. Before writing briefs, probe the assumptions the task rests on with a cheap agent (the route exists, the data is readable, the local environment runs). A reviewer is handed the diff as a file (`pk worktree review <ID>` writes it, with generated paths excluded, and a stat file naming what was left out), never pasted text; run it again before every re-check, and it moves the review worktree to the new commit. An implementer that handed back commits nothing more on its branch until the review returns.
- **C16. Resume, then start fresh.** Fix rounds and re-reviews resume the agent that holds the context. Record each run with `pk cost add`; when one agent of a task passes 400,000 tokens or three resumes, `pk cost report` and the hand-off flag it: stop resuming it and give a fresh agent a tight fix brief (the findings, the files, the commands).
- **C17. Verify, don't relay.** An agent's claim is not a fact until you have checked it. Spot-check the claims a decision rests on: a failure said to exist on main (reproduce it there), a timestamp, a read-back of what was written. Your report to the user says what you verified and what you did not.
- **C18. Batch the user's decisions.** Collect the decisions you need, give each a recommendation, ask once, and go on with everything that does not depend on the answers. A preference the user states once becomes a ruling.
- **C19. A hand-off that can be read whole.** `pk handoff check` fails when `program/HANDOFF.md` is over its budget (60 KB, raised only by a ruling: `pk record --handoff-budget`) or its Next steps section is over 2 KB. History lives in `program/rulings.md`; the hand-off shows the newest fifteen rulings. Triage follow-ups at every merge: close, tag to defer, or mark duplicates (`pk followups`).
- **C20. Finish what merged.** After a merge, `pk worktree finish <ID>` removes the task's worktrees and merged branch and, when given the task's compose project name, the containers and volumes that carry that project's compose label (an exact match, never a name prefix; images are left alone). It refuses a worktree that holds work (hard rule 22), one standing on a commit no branch holds, and git-ignored files it was not told to drop, and it never forces.
